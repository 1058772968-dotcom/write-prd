# 简洁交互与数据流转图

按当前产品真实流程选用和修改。下面是组织方式，不是需要一并引入的功能清单。

## 图的层级

- 第一章核心流程：只保留每项核心任务的起点、主要步骤、用户结果。
- 具体功能图：增加实际存在的条件、状态、数据输出、失败/取消和恢复。
- 一张图只讲一条可理解的业务路径；多个相对独立的任务分开画。宽度过大时拆图，而不是无限向右缩进。
- 节点用短语“动作 + 结果”，长规则放到限制条件表中。状态的转换用流程图表达，不用只有名词分支的思维导图替代顺序关系。

## 有输入和结果判断的通用流程

```plaintext
用户操作 / 设备触发 / 系统事件
  ↓
获取输入 → 检查前置条件与业务规则
  ├─ 不通过 → 说明原因 → 保留可保留内容 → 修正或退出
  └─ 通过 → 执行业务处理
              ↓
          判断实际结果
              ├─ 成功 → 更新状态 / 生成产出 → 继续下一步
              ├─ 明确失败 → 说明原因 → 按规则重试或取消
              └─ 部分完成 / 结果未知 → 保留已有结果 → 核实后恢复
```

删除本业务不存在的分支，不要求所有功能都有“提交”或服务端。

## 设备或实时功能的状态流转示例

```plaintext
用户选择功能 → 检查设备 / 权限 / 当前状态
  ├─ 不可用 → 提示对应原因 → 调整条件后返回
  └─ 可用 → 开始运行 → 显示当前状态
                         ├─ 用户暂停 → 暂停态 → 继续运行 / 结束
                         ├─ 正常结束 → 按规则生成或保留结果
                         └─ 异常中断 → 保护已有结果 → 告知恢复方式
```

是否支持暂停、后台执行或离线恢复，需按目标产品确定。不得默认设备断连后可无缝切换，也不得编造时间、容量或续航值。

## 内容处理或 AI 生成示例

```plaintext
输入内容 / 选择已有资料
  ↓
检查输入与可用额度（如本功能需要）
  ↓
开始处理 → 显示进行中
  ├─ 完成 → 展示产出 → 用户确认 / 编辑 / 使用
  ├─ 用户取消 → 按规则结束处理并保留已有内容
  └─ 失败或结果不明 → 显示实际状态 → 核实或重试
```

按实际方案补充数据来源、处理阶段、保存位置及下游使用者。“请求已发出”“生成完成”“保存成功”不能在业务有区别时混为一谈。不要未经依据写入固定模型名或接口。

## 版本与发布示例

```plaintext
新建 / 修改 → 保存草稿 → 预览
  ↓
明确发布本次版本 → 校验内容及权限
  ├─ 不通过 → 保留草稿与原公开版 → 修正
  └─ 通过 → 更新公开版 → 反馈结果
只编辑未发布 → 公开版不变
下架 → 停止公开展示 → 按既定规则保留源资料
```

只适用于实际存在草稿/发布流程的功能。不默认所有编辑都需要审批，也不自行加入审核人或时限。

## 输出图前的检查

1. 每个动作与正文里的需求对应，没有由模板引入的新功能。
2. 判断分支条件明确，成功、失败、取消或未知状态有合理去向。
3. 涉及多个阶段时，分别说明已完成结果与未完成步骤；例如保存与通知、付款与权益、生成与落盘。
4. 数据流标清输入、处理、产出及使用方向；只写有依据且帮助理解的存储或系统信息。
5. 重试、重复操作和中断恢复按风险与实际方案处理，不画成无条件重新执行全部动作。
6. 保持图可编辑、可读，与原型展示图分开。用户只留原型图位时，文字流程图仍正常输出。
